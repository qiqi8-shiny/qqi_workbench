📦 数据准备（A_data_prepare.py）
  • 源：FDA MAUDE 6 表，唯一键 MDR_REPORT_KEY；产品码筛选 ["JAK"]（CT 设备）。
  • 「关联」 = 将 6 张分表按主键合并成一张宽表，再做清洗/缺失值处理。
  • 字段自动定位（_pick_col）：日期列/厂商列/分组键不硬编码（大小写不敏感，先精确后包含）；找不到时报错并打印真实列名。
  • 打标 label_recalls()：按"厂商 + ±3 年窗"匹配召回库，命中→1，否则→0。（CT 课题打标统一在 A 步完成；专利项目曾后置，此处不同。）
  • 厂商名归一化 normalize_name()：规则标准化（小写 / 去标点 / 去公司后缀 inc|corp|medical|health|systems…）。

🧠 文本特征（B_text_preprocess.py）
  • BERT 系（BioBERT / ClinicalBERT，具体型号待与导师确认）取 [CLS] 句向量，batch 推理，落盘 text_embeddings.npy + cleaned_text.csv。
  • 不引入停用词（BERT 不需分词停用词）；clean_text() 仅 re.sub 去控制字符/非字母数字。
  • 文本预处理：输入 BERT 前只需轻量清洗——clean_text() 去控制字符/非字母数字，不做停用词、不做分词；BERT 自带 tokenizer 完成 tokenization/子词切分。清洗后可直接喂入 BERT。
⚠️ 待确认：开题报告 P46 写 ClinicalBERT、P68 写 BioBERT，两处未统一；代码当前默认 PubMedBERT，与 P68 不符，确认后改 BIOBERT_MODEL。

🔗 〔可选〕医学本体归一化（I_medical_ontology.py）

默认关闭
  • 目的：将自由文本中的同义医学术语归一化到标准概念（如 "wire broke" = "cable fracture"）。
  • 默认 USE_UMLS=False（本地同义词表顶着）；申请 UTS 账号后填 API Key、USE_UMLS=True 走在线接口（免整包下载）。
  • MedDRA 商业授权，学生不引；落地用 UMLS。非主线必备。
  • 厂商名归一化（A 步）与医学本体归一化（B 前）对象/阶段/是否必须均不同，分开两个脚本。

🔀 结构化特征 + 多模态融合（C_build_features.py）
  • encode_struct()：厂商 Top15 独热(prefix=mfr) + 事件类型独热(prefix=evt) + 年份(数值) + 文本长度(数值)。
  • np.hstack([bert_vec, struct_vec]) → StandardScaler 统一尺度。
  • 缺失值：year→中位数，event_type→"Unknown"。
  • 落盘 X_all.npy 为未经 SMOTE / 标准化的原始融合特征（供 H、Z 各自在划分后处理，防泄漏）。
  • ⚠️ 融合特征里虽含 year 数值，但那是"每条报告静态年份"，不含时间顺序/演变；时序演变由 H 用 date_received 排序序列补。

✂️ 划分
  • 静态支路：随机 80/20（random_state=42, stratify=y），在 C 内完成；验证集由 D 内 CV 充当。
  • 时间分割对照：静态走 Z_random_vs_time_split.py；时序走 H 内 SPLITS_TO_RUN=["random","temporal"]。
  • 关键纪律：标准化 / SMOTE 必须在划分之后、仅用训练集 fit，防泄漏（Z、H 均读取 C 的 X_all.npy 原始特征再各自处理）。

📊 EDA（F_eda_analysis.py）
  • 目的：在建模前/后展示数据分布与不平衡性，为论文第 3 章提供图 3-X 系列。
  • 内容：标签分布、召回率年份趋势、Top 厂商/事件类型占比、字段缺失率、文本长度分布。
  • 输出：5 张图存 output/eda_figures/；可直接嵌入第 3 章 EDA 节。

🔍 解释（E_shap_analysis.py / G_gini_importance.py）
  • SHAP 针对测试集；主模型取 min(1500, 测试集) 条，从测试集随机无放回抽样（np.random.choice(..., replace=False)），建议加固定 random_state 保证可复现（稳定性检验可 500/1000/1500/2000 都跑，论文只写"1500 条已趋稳"）。
  • 树模型用 TreeExplainer（RF/XGBoost 快）、线性/MLP 用 KernelExplainer（慢但通用）；最终输出全局重要性 Top10 与 summary plot。
  • Gini：D 最优模型的 Gini 重要性 Top5 与 SHAP Top5 对照，作为特征解释稳健性检查。
  • 时序支路 SHAP 暂缓（可后续用 DeepExplainer / GradientExplainer）。
  • SHAP 是训练后解释器、不学东西；"模型学关系 → SHAP 后解释"是先后两道工序。

顺序步骤在哪做关键纪律

静态支路代码逻辑（四段顺序 A+C → 列算法 → 设权重 → 网格搜索 → 训练）
①列算法 + 列参数
models 大字典，D 脚本中段；每个算法一项，括号内 params 是它要试的全部参数组合。
models 字典示例 点击打开代码
models = { "LogisticRegression": { "model": LogisticRegression(max_iter=1000, random_state=42, class_weight="balanced"), "params": {"C": [0.1, 1.0, 10.0]}}, "DecisionTree": { "model": DecisionTreeClassifier(random_state=42, class_weight="balanced"), "params": {"max_depth": [10, 15, 20, 25], "min_samples_split": [2, 5]}}, # ... RandomForest / SVM_Linear / MLP 同理（都带 class_weight="balanced"） # XGBoost 特殊：无 class_weight 参数 → 用 scale_pos_weight=正负样本比； # 且 n_estimators 已从网格移出（固定 2000 上限）+ early_stopping_rounds=50 # + fit_params 传 eval_set=（15% 监控集）→ 网格搜索里触发早停 }
②代价敏感
就写在第①步建模型对象时，不是 GridSearchCV 里、不是训练后。
class_weight="balanced"（每个模型构造时写入；权重在模型对象里预先设好，是模型自带属性，不进网格搜索参数表）
③开启网格搜索
把①里建好的模型〔已含②权重〕和参数表一起交给网格搜索。
GridSearchCV 调用 点击打开代码
grid = GridSearchCV(cfg["model"], cfg["params"], cv=3, scoring="f1_macro", n_jobs=1, verbose=0)
④开始训练
"列出最优参数 → 写 model=某算法(最优参数) → 训练"三步在 sklearn 里由 GridSearchCV 内部自动完成；训练数据是切掉 15% 监控集后的 X_tr（XGBoost 通过 fit_params 额外把监控集作为 eval_set 传给 early_stopping_rounds 触发早停）。
fit 与预测 点击打开代码
grid.fit(X_tr, y_tr, **cfg.get("fit_params", {})) # XGBoost 的 fit_params = {"eval_set":[(X_val, y_val)]} y_pred = grid.best_estimator_.predict(X_test) # 测试集预测

注：sklearn 省掉了手动 model = RandomForest(best_params); model.fit(...) 那两行，但本质就是 ②设权重 → ③网格搜索 → ④训练 这条链。

📋 设计要点
模型定位
集成学习为主：RF / XGBoost 对 BERT 高维大样本特征更稳，预期更优；LR / SVM / DT / MLP 作对照
超参调优
GridSearchCV cv=3：在训练集内做 3 折交叉验证选最优超参（不碰测试集）
基线划分
随机 80/20（stratify, seed=42），C 脚本完成；时间分割作对照放 Z
不平衡处理
SMOTE（过采样） + 代价敏感 class_weight='balanced'，二者互补（一个改数据分布、一个改损失权重）
网格搜索规则
只搜结构超参（C / max_depth / learning_rate …）；不搜 class_weight（全部固定 'balanced'）；XGBoost 的 n_estimators 也移出网格（固定 2000 上限，让早停定轮数）—— 避免"网格搜索定轮数"和"早停定轮数"打架
早停
训练时监控验证集，连续 N 轮不改善就停，省时间、防过拟合。MLP（max_iter=500 + early_stopping=True）和 XGBoost（rounds=50 + eval_set=监控集）都已启用
公平性
85% 的来源：C 已做随机 80/20 得到 X_train；D 一上来再从 X_train 切 15% 作监控集（只给 XGBoost/MLP 做早停用），剩 85%（=80%×85%）作为六算法的共同训练基底 —— 保证对比公平（同算法不同算法谁都不能多看/少看数据）

🔗 构造序列（核心步骤）

下面用你最熟的例子讲：某型号+某批号（简称"CT机 ABC批"）有 3 份不良事件报告，分别是 1月、2月、3 月，3 月这次被召回。

步骤做什么例子（1月 / 2月 / 3月）
① 找同一批在清洗好的 CSV 里，按型号 + 批号相同把报告归成一堆搜出 3 份报告，型号+批号都是"CT机 ABC批"
② 查时间排队看这堆里每份的 date_received，按时间从早到晚排1月 → 2月 → 3月
③ 滑动窗口截取在排好队的这列报告里，按"窗口长度 SEQ_LEN、步长 STRIDE=1"连续截取成若干段；每段错开 1 条、高度重叠12 条报告满窗后截成 [1–10]、[2–11]、[3–12] 等段；3 条报告截成 [1–2]、[1–3] 两段（每段即一个训练样本）
④ 打标签去召回库按型号+批号查：这批什么时候召回？（标签实际在 A 脚本已打好，H 只读取）召回发生在 3 月 → 这 3 份报告的标签全 = 1
⑤ 取特征每份报告的特征早在 C 脚本就融合好了；动态不再做新融合，只把窗口内已融合向量按时间顺序排成一列[ 1月融合向量 , 2月融合向量 , 3月融合向量 ]
⑥ 定序列标签这条时序序列的标签 = 窗口内最后一条（3月）的标签序列标签 = 召回（1）
⑦ 喂模型模型学"这三次怎么演变到最后一次召回"预测：给定前两次 + 第三次，这次会不会召回？
点击查看构造序列的核心代码（简化版） 点击打开代码
# 输入 # clean_csv : 清洗好的报告表（含 型号/批号/date_received/label） # X_all : C 脚本已融合好的特征矩阵（每行 = 一份报告的融合向量） df = read_csv(clean_csv) # groupby：一次扫描按「型号+批号」把相同报告归成一堆（哈希分桶，不是逐条去全表搜） for (model, lot), grp in df.groupby(["型号", "批号"]): grp = grp.sort_values("date_received") # ② 排队：1月 → 2月 → 3月 if len(grp) < MIN_REPORTS: # MIN_REPORTS=2，少于2条才跳过 continue # ③ 滑动窗口：从排好队的这批里，步长=1 连续截取成若干段 # e = 每段窗口的【末端位置】，每段长度不超过 SEQ_LEN=10 # 每一段同时完成：⑤取特征 / ⑥定序列标签 / ⑦输出序列 for e in range(MIN_REPORTS, len(grp) + 1, STRIDE): s = max(0, e - SEQ_LEN) # 窗口起点 win = X_all[grp.index[s:e]] # 这段的融合特征（≤10 行） label = grp["label"].iloc[e - 1] # 这段【最后一条】报告的 label 输出 win(前面补零到 SEQ_LEN 长度), label
关键澄清 1：SEQ_LEN=10 不是最低要求。同一批只有 3 条报告时，窗口就只取这 3 条，前面补 7 个"空位"（mask 标记忽略）——不会被踢掉。真正会踢掉的是报告数 < MIN_REPORTS=2 的批。
关键澄清 2：月份不写进特征。序列里只放融合向量，"1月/2月/3月"只用于排队；模型靠"第 1 个位置、第 2 个位置、第 3 个位置"知道先后。
关键澄清 3：动态不再做特征融合。融合在 C 脚本里逐条做完了，H 只是重新排列。
关键澄清 4：分组用 groupby，不是逐条全表搜。代码里 df.groupby(["型号","批号"]) 是一次性哈希分桶——把相同"型号+批号"的行归到同一堆，再逐个堆处理。你理解的"分堆"本质对，只是底层是哈希分桶、不是每来一个 key 就全表扫一遍。
关键澄清 5：滑动窗口是独立的第③步，位于②排队之后、④打标签/⑥定序列标签之前。同一批排好队后，按"窗口长度 SEQ_LEN、步长 STRIDE=1"从前往后滑，每段错开 1 条、高度重叠。例：12 条报告会滑出 [1–10]、[2–11]、[3–12] 等典型窗口；3 条报告会滑出 [1–2]、[1–3]。每段即一个训练样本，标签取该段"末条"报告。它让一个批能贡献多条序列，样本量得以提升。

时序支路全流程
环节做法
构造序列见上方「构造序列」卡片：同一型号+批号按 date_received 排序 → 滑动窗口（STRIDE=1）取最近 ≤SEQ_LEN=10 条 → 每条=该报告融合特征 → 序列标签=末条报告 label
排序职责100% 由本脚本预处理完成，下游 Transformer/LSTM 只消费已排好序的序列，不负责排序
不平衡仅代价敏感（CrossEntropyLoss(weight)），不做 SMOTE——SMOTE 插值会破坏时间结构 / mask
标准化仅在训练集上 fit（防泄漏），已补
划分随机（按组分组 GroupShuffleSplit，防重叠窗口泄漏）+ 时间，一次跑完出对比表
早停训练序列再切 15% 监控集，按验证集 AUC 早停（PATIENCE=10，EPOCHS=100 上限）；触发后恢复最佳轮次的权重再测测试集。测试集全程不参与早停判定（防泄漏）
超参除早停（监控集动态定轮数）外其余固定（神经网络网格搜索代价极高）；如需可选少量预设组合按验证集筛选
为什么序列标签取「末条报告的 label」？ 把同一批的多次报告看成一个整体输入，这个整体该打什么标签？用最后那条（最新）报告的 label 最自然——因为它反映的是"看到这段历史后，最新这次是否被召回"。训练时模型学的是"给定这几次报告的演化模式，预测最新这次是否召回"；测试时也这样：喂入一段历史，预测最新 1 条。
为什么数据量会减少 / "第一次发生"被剃掉？ 滑动窗口要"同一批里至少 MIN_REPORTS=2 条报告"才生成序列；只有 1 条的批会被跳过。对于能用的批，前几条报告因为"前面凑不够窗口"也不单独成序列（比如 3 条报告、SEQ_LEN=10 时，只产生 1 条以第 3 条为结尾的序列）。所以总序列数一定比原始报告数少。这不是 bug，而是时序建模的代价：用"能构成一段有效历史的序列"训练。

分类头（classification head）· 组件与作用
组件作用
proj（降维层）Linear(feat_dim → d_model=64)：把 BERT 768 + 结构化维度压到 64 维，再送主干
enc（主干 / backbone）TransformerEncoder 或 LSTM：提取序列特征，输出高维向量（本身无分类 / 概率功能）
cls（分类头）Linear(d_model → 2) + Softmax：把向量映射成"召回 / 非召回"概率
写在哪：分类头 = 接在 backbone 上的外接附件（Dense+Sigmoid/Softmax），不是 Transformer 内部。传统分类器（RF/LR/SVM/DT）出厂即带分类功能，故静态支路不用写、动态支路要写。它在定义模型时（训练前）与 backbone 同属一个模型类写好——不是训练后、也不是网格搜索后（动态本无网格搜索）。
